# 多级标签用 `/` 路径写在标签文本里，Emoji 属于文本，不引入标签实体

引入多级标签和侧栏标签树时，我们决定不改存储结构。标签仍是笔记上的字符串数组，层级靠标签文本里的 `/` 表达，标签树由客户端从这些字符串实时合成。Emoji 直接写在标签文本里，树上把某一级开头的 Emoji 显示为图标；只有大小写或空白不同的写法合成同一个节点。写入时由共享的规范化函数整理路径（去掉每段首尾空白和空段），服务端和 Web 输入端共用，存量数据不回填。重命名或移除一个节点时，由客户端把子树展开成多次现有的精确改名或删除，后端不新增写路径。这样不需要 Migration，也不需要新的同步实体，旧版 Android 和 iOS 继续把 `a/b` 当作普通标签处理，数据保持兼容。

## Considered Options

- **独立的标签实体或标签元数据表**（带父级、图标、颜色、排序，类似 flomo 给标签设图标）：可以单独设图标、手动排序，但要新增表、Migration 和同步实体，Web、桌面 sidecar、Android、iOS、MCP 都得适配，旧客户端还会遇到不认识的实体。
- **把现有 `tag` 查询参数直接改成包含子孙**：改动更少，但 Android 和 iOS 在线时会带出子孙、离线时仍是精确匹配，MCP 和公开笔记本站点的语义也会被连带改变。因此只新增 `tagAny` 等可选参数，旧语义不变。
- **服务端提供子树重命名接口**：单次请求就是原子操作，但合并规则要在 API、Web 本地镜像和 Rust sidecar 各写一遍，还要新增离线队列的动作类型。
- **只在 Web 输入端规范化**：不改服务端写入，也不需要跨版本验证，但 MCP 和移动端写入的不规范路径会一直留在数据里。

## Consequences

- 改一个父级标签，就要改写子树内每篇笔记的标签字符串。级联由多次精确操作组成，不是原子的；中途失败时，树上能看到部分完成的状态，再执行一次即可收敛。
- 换图标就是一次重命名。
- 标签只存在于笔记上：没有笔记使用的路径不会出现在树上，也不能预先建一个空标签。
- 规范化只作用于写入值。查找旧标签时仍按原文匹配，否则 `a / b` 这类旧写法就无法改名或删除。
